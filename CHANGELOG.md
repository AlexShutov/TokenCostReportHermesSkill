## 20.10.2026
### Эквивалентный кодовый план z.ai (месячное окно) — `scripts/plan_usage.py`
- Доработка по запросу пользователя: помимо прямой цены токенов считается использование эквивалентного кодового плана z.ai. Логика — дословно из docs.z.ai/devpack/overview (проверено чтением страницы): кредиты = (input × Input_mult + cached × Cached_mult + output × Output_mult) / 10000; GLM-5.3 = 6.9/1.7/24, GLM-5.3-Flash = 2.3/0.56/8; вне пика — 50% стандартной ставки; пик — пн–пт 14:00–18:00 Singapore (UTC+8); выходные — внепик весь день.
- **Месячного лимита на сайте нет** — публикуются только 5-часовой и недельный (Light 2000/10000, Pro 12000/60000, Max 28000/140000). Месячный лимит выводится: недельный сбрасывается каждые 7 дней от активации, месячное окно — от сохранённого дня начала отсчёта до того же числа следующего месяца, лимит = weekly × (дней_в_окне / 7). Блок обязан называть, что это вывод, а не опубликованное число.
- День начала отсчёта месяца сохраняется в `~/.hermes/state/token_cost_plan.json` (`--set-anchor 15` или дата); дефолт 1 помечается `default`, пока пользователь не установил свой. Якорь 31 в месяце без 31-го числа берёт последний день месяца — ограничение называется.
- Каскад Light → Pro → Max по правилу пользователя: излишек переносится на следующий план; строка `использовано X% Y плана`.
- Пик/офф-пик считаются по временным окнам инкрементов (доля окна в пике → коэффициент `frac × 1.0 + (1 − frac) × 0.5`); точечные строки (backfill/first_seen) решаются по моменту и называются оценкой.
- Ограничения, названные в блоке: MCP-вызовы (1.2 кредитов за вызов) не отслеживаются и в блок не включены; модель без опубликованных мультипликаторов считается мультипликаторами эквивалентной модели и называется; локальные токены в план не входят, anomaly не входит в sums, строки вне месячного окна исключаются.
- Блок деградирует честно: без базы заголовок и оговорка о выводе печатаются, кредиты не считаются, и блок это называет.
- `tests/test_plan_usage.py` — 29 проверок (stdlib, offline). Pitfall: модуль, который решает пути при импорте, остаётся с прежним временным HOME — тест обязан выгружать `plan_usage` из `sys.modules` в setUp, иначе блок читает базу предыдущего теста (это и был первый падёж).
- `tests/clean_install.py`: два новых проверки блока плана (заголовок и оговорка о выводе), тесты запускаются оба файла.
- Живой прогон на этой машине (2026-10-20): 2270.8 кредитов за месячное окно → использовано 5.1% Light плана (месячный лимит 44285.7); пик 0.0% — все z.ai-строки окна попали в офф-пик.

## 18.10.2026
### Баги, найденные тестами (27 тестов, stdlib, Python 3.9)
- `plan_class` не учитывал `billing_base_url`: строка с provider='custom' и маршрутом на api.z.ai считалась локальной в суточном блоке и z.ai в блоке «не учтено» — одни и те же токены в двух категориях. Теперь признак z.ai тот же, что у SQL-фильтра.
- Исчезнувшая между запусками строка никогда не попадала в базу как anomaly (документация это обещала): `record_run` перебирал только текущие строки. Добавлен разбор ключей последнего наблюдения — удаление сессии теперь видно.
- `bump_ledger` писал копилку без `os.makedirs` → на чистой установке (каталога `~/.hermes/state` нет) первый запуск падал с FileNotFoundError и отчёт не формировался.
- `fetch_prices`/`fetch_rate` были не тестируемыми (сеть внутри функции) — выделены чистые `parse_price_table(html)` и `fetch_rate_from_text(text)`; у курсового шаблона валюта теперь необязательна, но дробное число обязательно — цена карты «2 990₽» по-прежнему не проходит.
- Строка «с 21:00 предыдущего запуска» печаталась, когда запуска 21:00 в базе ещё нет (метка врёт). Теперь печатается честно.
- Блок z.ai называл оплаченные токены «coding plan». Теперь план и оплата разделены.
- `T.connect()`/`record_run` были без guard: заблокированная база роняла весь отчёт. Теперь отчёт выходит старым путём с честной пометкой; тик не роняет крон-задачу.
- Профиль для cron: `HERMES_PROFILE` cron-ом не устанавливается (его ставит только kanban-диспетчер), поэтому профиль читается из записи задачи в `jobs.json`.
- Обёртки крона имели абсолютный путь автора (`/Users/alex/.hermes/scripts/...`) — на машине коллеги крон падает. Путь решается относительно самого файла.
- `CHAT_ID` был жёстко прописан чатом автора — на другой машине блок «За текущую сессию» относился бы не к тому пользователю. Теперь `TOKEN_COST_CHAT_ID`, и отчёт называет, если routing-запись не найдена.
- Ограничение (не баг, названо в SKILL.md): инкремент, окно которого пересекает границу суточного окна, считается целиком — при длинном интервале между запусками прирост целиком попадает в день `window_end`.
- Добавлены `tests/test_token_cost.py` (27 проверок) и `tests/clean_install.py` (чистая установка: клон из локального репо, временный HOME, setup.sh, полный прогон всех режимов), `scripts/setup.sh`.

### Append-база статистики + фикс суточного окна (короткая сессия)
- Новый `scripts/token_cost_db.py`: append-only SQLite (`~/.hermes/state/token_cost.db`), три таблицы — `runs` (таймстамп каждого запуска, job, cron-задача, профиль, сессия, цены и курс на момент запуска), `usage_snapshot` (каждое значение source-строки на момент запуска), `increments` (прирост каждой строки между наблюдениями с временным окном). Ничего не удаляется — только INSERT.
- Суточное окно и «по дням» считаются суммированием инкрементов по временным окнам, а не дельтой от снимка 21:00. Баг: при короткой сессии «за последние сутки» печатал $0.00, хотя фактическое окно 24 ч было $2.60 (замерено живым прогоном на этой машине).
- `plan_class` различает z.ai coding plan и оплату по факту: `zai_plan_by_rule` (правило пользователя), `zai_paid` (списаны деньги — сильный сигнал по `actual_cost_usd`), `local` (любой не-z.ai), `unknown`. `billing_mode` для z.ai в этой машине пуст или `chat_completions` — по нему план не определяется.
- Атрибуция времени: `delta` (настоящий интервал между запусками), `first_seen`, `backfill` (строки до создания базы — атрибутированы точкой `last_seen`, это оценка), `anomaly` (уменьшение/исчезновение строки — в суммы не входит, но остаётся в базе).
- Ограничение честно называется в отчёте: токены до создания базы нельзя разложить по времени.
- Проверено живым прогоном: база сходится с source-таблицей в пределах роста между запросами (разница 1.4K/374K/2.3K токенов — токены этого же сеанса), двойного счёта нет; тик пишет run с `cron_job='token-counter'` и delta-инкремент, stdout остаётся пустым.

### Только локальные LLM + копилка экономии (правило пользователя)
- Статистика считает ТОЛЬКО токены локальных моделей (фильтр `billing_provider`/`billing_base_url` по NOT z.ai в `session_model_usage`); токены z.ai coding plan не считаются — они идут по лимиту подписки.
- Экономика = сколько стоили бы локальные токены по ценам z.ai (GLM-5.3-Flash): input $0.15, cached $0.03, output $0.50. Копилка-леджер (`token_cost_ledger.json`) суммирует только прирост, удаления сессий не обнуляют.
- База суточной дельты хранит значения копилки на 21:00, а не привязку к session_id — переживает смену/удаление сессии и смену модели.
- Формат: «за всё время» убрано, вместо него разбивка «По дням» за последние 4 дня.
- Cron: token-cost-daily (21:00, --commit через token_cost_commit.py) + token-counter (каждые 10 мин, --no-agent, token_cost_tick.py — обновление копилки без LLM).
