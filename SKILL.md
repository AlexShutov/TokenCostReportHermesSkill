# Token cost report (экономия на локальных LLM)

## Когда использовать
Когда срабатывает ежедневный отчёт в 21:00, или когда пользователь спрашивает про статистику токенов / сколько он сэкономил на локальных LLM.

## Что считается (правило пользователя, 2026-10-18)
- Канонический скрипт: `~/.hermes/scripts/token_cost.py` (крон требует скрипты в `~/.hermes/scripts/`).
- Считаются ТОЛЬКО токены, обработанные локальными LLM (strata :8080, LM Studio, ollama, bionic — любой провайдер, кроме z.ai). Фильтр по таблице `session_model_usage`: исключить строки `billing_provider='zai' OR billing_base_url LIKE '%api.z.ai%'`.
- Токены z.ai coding plan НЕ считаются (идут по лимиту подписки). Экономия = сколько стоили бы локальные токены по ценам z.ai (GLM-5.3-Flash): input $0.15, cached $0.03, output $0.50.
- Копилка (ledger, `~/.hermes/state/token_cost_ledger.json`): суммирует только прирост `last_seen → cur`; удаление сессий (просадка cur) не обнуляет накопленное. Обновляется каждым недрым запуском, включая ручной и тик.
- База суточной дельты (`~/.hermes/state/token_cost_snapshots.json`) хранит значения КОПИЛКИ на 21:00, а не привязку к session_id — прежняя привязка теряла базу при смене/удалении сессии (случилось 2026-10-18).
- Статистика НЕ сбрасывается при смене модели — копилка сквозная.
- Крон-задачи: агентные тратят токены (по умолчанию qwen на strata), но `--no-agent` джобы (rain-golovinsky, token-counter) выполняют скрипт без LLM — ноль токенов.
- Цены z.ai — живые при каждом полном запуске (страница парсится по заголовку таблицы). При неудаче — сохранённая копия `~/.hermes/state/token_cost_prices.json`, в конце сообщения появляется пометка (передавать дословно). Ни сайта, ни кэша — `DEFAULTS` (input $0.15 / cached $0.03 / output $0.50).

## База (append-only) — `scripts/token_cost_db.py`, `~/.hermes/state/token_cost.db`

Каждый запуск (тик крона, полный запуск 21:00, ручной) пишет три таблицы. Ничего не удаляется — только INSERT.

- `runs` — таймстамп запуска, job (`tick`/`commit`/`manual`), cron-задача, профиль, сессия, цены на момент запуска, курс и его источник (`live`/`cache`/`default`), значения копилки.
- `usage_snapshot` — каждое значение source-строки (`session_model_usage`) на момент запуска: session_id, model, billing_provider, billing_base_url, billing_mode, task, plan_class, токены, actual_cost_usd, first_seen, last_seen.
- `increments` — прирост каждой строки между двумя наблюдениями, с временным окном `[window_start, window_end]`. Суточные и сессионные значения считаются **суммированием инкрементов по временным окнам**, а не дельтой от базы снимка — короткая сессия больше не обнуляет «последние сутки» (это был баг: отчёт за сутки печатал $0.00, когда фактическое окно 24 ч было $2.60).
- `plan_class` различает: `zai_plan` / `zai_plan_by_rule` (подписка, в экономию не считается), `zai_paid` (z.ai, но реально списаны деньги — сильный сигнал по `actual_cost_usd`), `local` (любой не-z.ai: strata, LM Studio, ollama, bionic), `unknown` (провайдер не записан). Hermes `billing_mode` для z.ai в этой машине пуст или `chat_completions` — план по нему не определяется, поэтому класс строится по правилу пользователя и помечается `by_rule`.
- Атрибуция времени: `delta` (настоящий интервал между запусками), `first_seen` (строка впервые увиденная — окно first_seen..last_seen), `backfill` (строки, существовавшие до создания базы — атрибутированы точкой `last_seen`, это оценка), `anomaly` (строка уменьшилась ИЛИ исчезла между наблюдениями — в суммы не входит, но остаётся в базе; исчезновение обнаруживается сравнением ключей последнего наблюдения с текущими строками).
- `gap` — интервал между наблюдениями длиннее порога (переменная `TOKEN_COST_MAX_WINDOW`, по умолчанию 1800 с = 30 мин; ровно порог — это `delta`, не `gap`). Такой интервал выбрасывается из всех сумм (суточное, сессионное, месячное окна), но строка остаётся в базе (append-only). Причина: токены за длинный интервал реальны, но время внутри него не атрибутируется — пик/офф-пик по такому окну даёт оценку, которая не должна входить в оценку плана; расчёт обязан сразу выдавать результат, а не пытаться разложить получасовое окно. Отчёт обязан назвать число интервалов, токены и порог — иначе цифра выглядит как полная. Порог задаётся переменной окружения; тесты на обе ветви (выбрасывается / не выбрасывается при пороге 0). Подсчёт выбрасываемых интервалов обязан фильтровать по плану: оценка считает только плановые строки, иначе в счёт попадают локальные. Форма возврата одинакова для обоих путей источника (число токенов) — контракт описан в абстрактном классе.
- Оба пути — окна базы и блок плана — используют ОДНО определение исключённых атрибуций (через общий модуль). Раньше путь ядра имел своё условие (только anomaly), и выбрасываемый интервал попадал в кредиты плана; тест сверяет оба пути на одном наборе строк.
- Пометка про базу обязана печататься: раньше она собиралась и никогда не выводилась — правила про anomaly / unknown / выбрасываемые интервалы не доходили до пользователя.
- Ограничение (называть в отчёте): инкремент, окно которого пересекает границу суточного окна, считается ЦЕЛИКОМ — при длинном интервале между запусками (крон не работал, машина спала) прирост целиком попадает в день `window_end`.
- Первый запуск базы — `backfill`: токены до создания базы нельзя разложить по времени, они приписаны точке `last_seen`. Это ограничение, не баг; в отчёте оно называется.
- Проверено живым прогоном: база = source-таблица в пределах роста за секунды между запросами (разница 1.4K/374K/2.3K токенов — токены этого же сеанса), двойного счёта нет; тик пишет run с `cron_job='token-counter'` и настоящий delta-инкремент, stdout пустой.

## Эквивалентный кодовый план z.ai (месячное окно) — `scripts/plan_usage.py`

Логика — дословно из docs.z.ai/devpack/overview (проверено живым чтением 2026-10-20):
- кредиты модели = (input × Input_mult + cached × Cached_mult + output × Output_mult) / 10000
- мультипликаторы: GLM-5.3 = 6.9 / 1.7 / 24; GLM-5.3-Flash = 2.3 / 0.56 / 8
- вне пика модель списывается по 50% стандартной ставки; пик — пн–пт 14:00–18:00 Singapore (UTC+8); выходные — внепик весь день
- MCP-инструменты: вызов × Output_mult (1.2) — у нас не отслеживается, в блок не включается (названо в блоке)

**Месячного лимита на сайте нет** — публикуется только 5-часовой и недельный: Light 2000/10000, Pro 12000/60000, Max 28000/140000. Поэтому месячный лимит — вывод: недельный сбрасывается каждые 7 дней от активации, месячное окно = от сохранённого дня начала отсчёта до того же числа следующего месяца, лимит = weekly × (дней_в_окне / 7). Блок обязан называть, что это вывод, а не опубликованное число.

- День начала отсчёта месяца сохраняется в `~/.hermes/state/token_cost_plan.json` (`--set-anchor 15` или дата `2026-10-15`); дефолт — 1, источник помечается `default`, пока пользователь не установил свой. Если дня якоря нет в месяце (якорь 31, февраль) — берётся последний день месяца, это ограничение называется.
- Ядро блока — `scripts/plan_core.py` (SOLID: абстракции `PeakModel`, `CreditCalculator`, `IncrementSource`, реестры планов/мультипликаторов, `PlanCascade`, `OverflowLedger`, `PlanStateStore`, `TransitionNotifier`, `PlanReport`); `plan_usage.py` — CLI-обёртка, `token_cost.py` — прежний расчёт токенов (частный случай, вызывается только после переполнения Max).
- Два пути пика за одним интерфейсом `PeakModel.share(day, window_start, window_end)`: `WindowPeakModel` (доля окна в пике) и `DayIntegralPeakModel` — интегральная оценка по дню (для буднего дня 4/24 = 1/6, суббота и воскресенье — 0), без опоры на момент запроса. Дефолт — интегральный; `--peak window` возвращает оконный. Оконный путь при отсутствии окна падает на дневную интегральную оценку.
- Пик/офф-пик считаются по временным окнам инкрементов: доля окна в пике → коэффициент `peak_frac × 1.0 + (1 − peak_frac) × 0.5`. Это приближение, и блок обязан так его называть: z.ai списывает по моменту каждого запроса, а база хранит окна между наблюдениями, поэтому пик делится по времени окна пропорционально, а не поштучно. Точечные окна (backfill/first_seen) решаются по моменту — это оценка, блок называет число таких строк.
- Каскад по правилу пользователя: Light → Pro → Max. Когда месячный лимит Light исчерпан, излишек считается по максимальному лимиту Pro; когда Pro исчерпан — по Max. Строка: `использовано X% Light плана` (при переходе — несколько строк, по одному плану на строку).
- Считаются только z.ai-строки (`zai_plan`, `zai_plan_by_rule`, `zai_paid`); локальные токены в план не входят. Anomaly в sums не входит. Строки вне месячного окна исключаются.
- Строки базы ДО начала месячного окна не входят в оценку и должны называться отдельной строкой блока. Если якорь отсекает данные, уже имеющиеся в базе, сказать это прямо и предложить перенести якорь на первую дату базы — расхождение буквального выбора якоря с целью («все данные в расчёт») решается вопросом, а молчанием.
- Переход плана сообщается на следующем cron-запуске: `Превышен план X, перешли на Y`; при переполнении Max — `План Max переполнен, переходим на пересчет токенов`. Состояние плана обновляется в обеих ветвях (и в ветке расчёта токенов тоже) — иначе переход сообщается заново на каждом запуске.
- Эквивалентная модель по умолчанию — GLM-5.3-Flash (`--model`); `--by-actual-model` считает мультипликаторами фактической модели каждой строки. Модели без опубликованных мультипликаторов считаются мультипликаторами эквивалентной модели и называются в блоке.
- Блок деградирует честно: если база недоступна, заголовок и оговорка о выводе печатаются, кредиты не считаются, и блок это называет.
- `--dry-run` не пишет ни файла состояния, ни базы.

## Переносимость (для чужой машины)

- `TOKEN_COST_CHAT_ID` — Telegram chat id пользователя. Без неё навык использует чат автора (362122320) и отчёт честно говорит, что routing-запись не найдена.
- Обёртки крона решают путь к `token_cost.py` относительно самого файла — абсолютный путь автора не используется.
- Профиль для cron читается из записи задачи в `~/.hermes/cron/jobs.json` (cron НЕ устанавливает `HERMES_PROFILE` — его ставит только kanban-диспетчер).
- `~/.hermes/state/` создаётся при первом запуске; крон исполняет скрипты только из `~/.hermes/scripts/`.

## Output format (standing user rule)
**Правило пользователя (2026-10-20, закреплено тестом): из всего вывода доставляется ровно две
строки** — `Равно X% плана Y на Z.ai` и `Эквивалентный кодовый план z.ai (эквивалентная модель
<модель>)`. Оговорки (месячное окно, вывод месячного лимита, модель пика, точечная атрибуция,
unknown-строки, anomaly, выбрасываемые интервалы, MCP, состояние плана) — это размышления: они
пишутся в лог (stderr) и остаются в базе, откуда восстанавливаются запросом, но в сообщение не
ходят. Форма ниже — только частный случай переполнения Max: версия про токены включается, когда
каскад Light+Pro+Max переполнен, и показывает только переполнение, а не общее количество токенов.
В навыке нет места для рассуждений модели: расчёт, формат и отправка — Python3-скрипт, который
работает и при отключённой LLM.
Отчёт начинается с интегральной оценки: `Равно X% плана Y на Z.ai` (X — процент плана, Y — тип плана), затем блок плана. Прежний расчёт токенов — ЧАСТНЫЙ СЛУЧАЙ: применяется только когда переполнен план Max, и показывает только число переполнения (вычет лимитов каскада Light+Pro+Max), а не общее количество токенов; суточное, сессионное и «по дням» берутся из того же расщепления. Форма частного случая — keep exactly this shape:
```
Сравнительная цена токенов — только локальные LLM (z.ai не считается)

Сэкономлено за последние сутки (локальные токены по ценам GLM-5.3-Flash):
- вход: <N>M × $0.15 = $<x> (₽<x>)
- кэш-вход: <N>M × $0.03 = $<x> (₽<x>)
- выход: <N>M × $0.50 = $<x> (₽<x>)
- итого $<x> (₽<x>)
- с 21:00 предыдущего запуска: $<x> (₽<x>)
- в среднем за час: $<x> (₽<x>)

За текущую сессию (локальные токены):
- вход: ...
```

- `token-cost-daily` (id `a4f0bff6e8dc`): `--no-agent` — в ходу нет LLM, скрипт сам считает,

- `token-counter` (id `ee33ad768298`): каждые 10 минут, `--no-agent` (скрипт = задача, без LLM — ноль токенов), скрипт `token_cost_tick.py` (`--tick`: обновить копилку, stdout пуст = тихо), deliver `local` + failure-deliver `local` — в Telegram не спамит.

## Pitfalls
- `messages.token_count` NULL — только агрегаты из `session_model_usage`; БД открывать `mode=ro` (гейтвей держит write-локи).
- Фильтр локальности — по `billing_provider`/`billing_base_url`, НЕ по имени модели: в одной сессии бывают строки нескольких моделей/провайдеров, а `sessions.model` хранит только последнюю.
- Копилка считает только токены, увиденные после её создания (2026-10-18): ранее удалённые сессии в «за всё время» не входят — это недооценка, не баг.
- Суточная дельта считается от копилки, поэтому переживёт смену сессии, удаление сессии и смену модели.
- При тестах — `--dry-run` (не пишет ничего: ни копилку, ни снимок, ни кэши).
- Крон исполняет скрипты из `~/.hermes/scripts/`, а не из директории навыка: правка исходников в навыке не меняет живой отчёт, пока копия не обновлена. После правки — diff задеплоенного файла с закоммиченным и проверка, что НОВЫЕ модули (например `plan_core.py`) тоже лежат в `~/.hermes/scripts/`; живой прогон делать из задеплоенного пути.
- Тесты чистой установки клонируют закоммиченное состояние, а не рабочее дерево: прогон до коммита проверяет прежнюю версию и проходит, когда новые проверки ещё не видны. Коммит — перед прогоном чистой установки.
- `plan_usage.py --set-anchor` печатает весь блок плана, поэтому запуск его в одной цепочке с отчётом даёт дублированный блок — сеттер якоря запускать отдельно, отчёт отдельно.
- Проверка арифметики расщепления идёт классами самого модуля, по фактическим сигнатурам: `StandardCreditCalculator()` без аргументов, `MultiplierRegistry` — через `for_model(model)` (не subscript), словарь токенов несёт ключ `cached` (не `cache`), строка инкремента обязана иметь `model`. Строка на 7000M токенов → 939 166.7 кредитов при коэффициенте 7/12; вычет каскада 44 285.7 + 265 714.3 + 620 000 = 930 000 → переполнение 9 166.7 кредитов = 68.32M токенов — совпадает с ручной проверкой, это и есть контрольный кейс.
- Общий SQL-фрагмент (условие исключённых атрибуций) сам добавляет плейсхолдеры — каждый вызывающий обязан передавать и их аргументы. Сверять число плейсхолдеров с числом аргументов в каждом месте вызова: расхождение даёт ошибку подстановки на живом прогоне, а тесты on-memory-пути её не видят.
- Тест обязан утверждать через функции сумм модуля (`window_sum`, `session_sum`, `daily`), а не через прямой `SELECT` к таблице: прямой запрос обходит фильтр исключений и тест проходит на сломанной логике.
- Тест сравнивает оба пути источника (in-memory и SQLite) на одинаковых строках — живой прогон идёт по SQLite-пути, поэтому расхождение форм или значений видно только там.
